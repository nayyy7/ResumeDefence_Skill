# Resume Defense Coach

> 基于真实简历与项目经历的动态追问式模拟面试 Skill

---

## 1. 项目简介

**Resume Defense Coach** 是一个纯 Agent Skill，模拟研究生复试、保研、科研面试或技术实习面试中面试官围绕简历项目连续追问的真实场景。

与传统题库式面试准备不同，本 Skill 的核心能力在于：

- **阅读**用户的真实简历和项目材料；
- **动态追问**——下一题永远由用户上一轮回答和整体覆盖状态共同决定；
- **严格分离**面试阶段和复盘阶段——面试时不评分不纠错，结束后才统一复盘；
- **证据约束**——所有项目事实必须 grounded 在用户提供的材料上，不编造。

---

## 2. 用户痛点

准备考研复试和技术面试的学生常遇到这些问题：

- 能背诵项目介绍，却无法应对面试官的深入追问；
- 不知道自己的回答具体错在哪里；
- 简历中使用了夸大或模糊的表述，在实际面试中会被反复质疑；
- 无法区分团队成果和个人贡献；
- 对项目中涉及的技术概念理解停留在表面。

本 Skill 通过模拟真实面试 + 结构化复盘，帮助学生暴露问题、修正错误、提升面试能力。

---

## 3. 纯 Skill MVP 的工作方式

当前版本是一个纯 Skill，具有以下特点：

- **零依赖**：不需要安装 Python 包、不需要配置数据库、不需要启动服务。
- **单文件入口**：`SKILL.md` 是唯一入口，包含完整的工作流定义。
- **支持文件驱动**：复杂的题目分类、追问策略、评分标准和模板拆分到 `references/`、`templates/` 和 `examples/` 目录中。
- **模型即引擎**：所有推理、判断、追问和报告生成都由大模型完成，不依赖外部脚本。

### 工作流

```text
读取简历与项目材料
→ 提取项目事实和可疑点
→ 制定隐藏的面试计划
→ 提出首个问题
→ 分析用户回答
→ 动态决定追问或切换主题
→ 完成整轮模拟
→ 逐题点评与纠错
→ 生成更优回答
→ 输出个性化复习计划
```

## 5. 如何使用

### 前提条件

- 使用支持 Agent Skill 的平台（如 Cursor、Claude Code）。
- 将 `resume-defense-coach/` 目录放置在项目的 `.cursor/skills/` 或对应平台的 Skill 目录中。
- 准备好你的简历、项目经历或相关材料。

### 推荐输入格式

准备好以下内容会让模拟效果更好：

- **简历**：包含项目经历、职责、技术栈和成果；
- **面试类型**：考研复试 / 保研 / 科研面试 / 算法实习 / AI产品实习；
- **目标方向**：目标学校/专业/岗位；
- **难度**：初级 / 中级 / 高级；
- **题量**：建议 8 道主问题；
- **补充材料**（可选）：项目报告、论文、README、PPT、实验记录。

### 示例启动语句

```text
请使用 resume-defense-coach Skill，根据我上传的简历进行一轮考研复试模拟。难度中等，8 道主问题。面试时一次只问一个问题，最后再统一点评。
```

```text
这是我的项目经历[粘贴内容]。像面试官一样连续追问我就行，不要给我一口气列一堆问题。难度可以高一点。
```

```text
我在 AI 产品团队实习过，负责了智能客服项目。请模拟一轮 AI 产品实习面试，侧重产品思维和模型能力边界。
```

### 交互命令

在面试过程中，你可以随时说：

| 表达 | 效果 |
|---|---|
| "开始模拟" / "开始面试" | 开始或继续面试 |
| "下一题" | 跳过当前题（不点评） |
| "结束模拟" / "开始复盘" / "点评" | 立即进入复盘 |
| "提高难度" / "降低难度" | 调整后续问题深度 |
| "只问某个项目" | 聚焦指定项目 |
| "重新回答" | 替换上一轮回答 |
| "我不知道" | 记录薄弱点，换题 |

## 6. 核心 Agent Workflow

### 对话状态机

```text
INTAKE（收集输入）
  ↓
MATERIAL_ANALYSIS（分析材料，提取项目事实和可疑点）
  ↓
INTERVIEW_PLANNING（制定隐藏面试计划）
  ↓
INTERVIEWING（一次一问，动态追问）
  ↓
ENDING_CHECK（判断是否结束）
  ↓
REVIEWING（逐题复盘、纠错、评分、复习计划）
  ↓
COMPLETED
```

### 深度阶段（V1.1）

整轮面试由浅入深，默认沿以下阶段推进：`PROJECT_OVERVIEW` → `PERSONAL_CONTRIBUTION` → `METHOD_REASONING` → `IMPLEMENTATION` → `TECHNICAL_DEPTH` → `CHALLENGE`。阶段不强制按序完成，允许自然追问打乱；切换项目时从该项目的 overview 重新起弧。开场不会直接问细粒度技术参数或底层原理。

### 两个严格分离的阶段

| 面试阶段 | 复盘阶段 |
|---|---|
| 面试官角色 | 教练角色 |
| 一次只问一个问题 | 逐题点评 |
| 不评分 | 1-5 分锚定评分 |
| 不纠错 | 概念纠错 + 优化回答 |
| 不给答案 | 提供示范回答 |
| 不透露评分标准 | 解释评分依据 |

## 7. 动态追问逻辑

这是本 Skill 区别于普通固定题库 Prompt 的核心。

每次收到用户回答后，按优先级依次检测：

```text
1. 是否真正回答了问题？
2. 是否和简历或材料冲突？
3. 是否使用"我们"但没有说明本人职责？
4. 是否提出了没有证据的数据？
5. 是否提到技术术语但没有解释？
6. 是否只描述做了什么，没有解释为什么？
7. 是否忽略替代方案、限制或失败案例？
8. 当前主题是否值得继续深入？
9. 是否应切换至尚未覆盖的能力维度？
```

### 追问优先级

1. 材料冲突或事实不一致
2. 个人职责不清
3. 效果数据无证据
4. 关键技术概念错误
5. 回答空泛
6. 方法选择缺少理由
7. 缺少替代方案和取舍
8. 缺少限制与失败分析
9. 进一步提高技术深度
10. 切换至新主题

### 追问模式（V1.1）

开始面试前会询问一次"是否开启追问"：

- **开启（默认）**：根据回答动态深挖，同一知识点默认最多连续追问 2–3 层；
- **关闭**：回答后不追问，直接进入下一道核心问题；错误、漏洞和遗漏统一记录，在最终复盘反馈（复盘报告第九节"未当场追问的问题记录"）。

### 单次问题数量与多项目覆盖（V1.1）

- 每轮只提 **1 个核心问题**，最多包含 2 个高度相关的子问题，禁止一次连问 3 个及以上问题。
- 多项目简历会先建立覆盖计划（如 8 道核心问题分配为 A:3 / B:3 / C:2），追问不计入配额，结束前检查是否有重要项目被遗漏。

## 8. 评分机制

采用 **1–5 分锚定评分**，10 个维度，禁止只凭感觉打分。

| 维度 | 描述 |
|---|---|
| 1. 项目动机与问题理解 | 是否清楚为什么做这个项目 |
| 2. 个人贡献与项目所有权 | 能否区分个人工作和团队工作 |
| 3. 技术准确性 | 概念和原理是否正确 |
| 4. 方法选择与取舍 | 是否理解为什么选这个方法 |
| 5. 实验、指标与证据意识 | 数据是否有依据 |
| 6. 对限制和失败的认识 | 是否了解项目的局限 |
| 7. 逻辑结构 | 回答是否有条理 |
| 8. 表达清晰度 | 是否准确清晰地表达 |
| 9. 追问应对能力 | 能否应对深入追问 |
| 10. 领域理解与未来思考 | 是否了解领域趋势 |

每个分数必须有具体依据。未覆盖的维度标记为"未充分评估"。

## 9. 事实约束与防幻觉设计

### 信息三分类

1. **明确事实**：用户材料中明确写出的内容；
2. **用户口述事实**：用户在面试回答中补充的内容；
3. **待确认推测**：模型根据材料推断的内容，不能当作事实。

### 禁止编造

Skill 不得编造用户的职责、团队规模、数据集大小、模型名称和参数、准确率/召回率等指标、baseline、用户访谈数量、项目是否上线、创新成果。

### 优化回答占位符

当缺少关键事实时使用：

- `[请补充真实的样本数量]`
- `[请补充实际使用的评测指标]`
- `[请明确你本人负责的模块]`
- `[请核实该提升比例]`
- `[项目材料中未提供这一信息]`

### 概念纠错置信度

复盘时区分：明确错误 / 表述不严谨 / 信息不足无法判断 / 可能正确但需材料支持。

## 10. 测试方法

### 手工测试

使用 `examples/sample-resume.md` 作为输入，验证以下场景：

1. **空泛回答** → Skill 应追问具体内容
2. **方法名词堆砌** → Skill 应选一个关键模块深入
3. **无依据指标** → Skill 应追问 baseline 和评测方法
4. **强回答** → Skill 应提高难度
5. **提前结束** → Skill 应立即进入复盘

### 评测案例

`evals/eval-cases.md` 包含 23 个评测案例，覆盖：

- 5 个正向触发案例（应激活 Skill）
- 4 个不应触发的案例
- 9 个边界案例
- 5 个 V1.1 功能案例（Case 19–23）：
  1. 单题不会出现超过 2 个子问题
  2. 面试整体由 high-level 逐渐进入 technical detail
  3. 三个项目的简历不会只询问其中一个
  4. Follow-up OFF 时不会根据回答继续追问
  5. Follow-up ON 时可以正常动态追问

## 11. 当前限制

- ❌ 纯 Skill 版本，无前端界面
- ❌ 无用户登录和会话历史记录
- ❌ 不支持跨会话的学习档案
- ❌ 不支持语音输入
- ❌ 不支持 RAG 检索原始材料进行事实核对
- ❌ 不连接招聘网站或学校题库
- ❌ 不统计真实答题时长
- ❌ 面试质量和追问深度依赖底层模型能力
- ❌ 无法对用户录取概率作任何保证

## 13. 核心设计原则

1. **材料理解**：从真实项目材料中提取可考察内容；
2. **动态决策**：根据回答选择追问深度和方向；
3. **阶段控制**：严格分离模拟面试和教学复盘；
4. **可评测性**：明确的评分标准、测试案例和验收规则。

## 14. V1.1 更新记录（2026-08）

1. **单次问题数量限制**：每轮 1 个核心问题，最多包含 2 个高度相关的子问题，禁止一次连问 3 个及以上问题；问题适合口头回答。
2. **面试深度阶段**：`PROJECT_OVERVIEW` → `PERSONAL_CONTRIBUTION` → `METHOD_REASONING` → `IMPLEMENTATION` → `TECHNICAL_DEPTH` → `CHALLENGE`，整体由浅入深，不机械执行，允许自然追问打断。
3. **多项目覆盖计划**：识别简历中全部主要项目，按重要程度/简历篇幅/目标方向/可追问价值分配核心问题配额（如 A:3 / B:3 / C:2），追问不计入配额，结束前检查未覆盖项目。
4. **追问开关**：面试开始前询问是否开启追问。关闭时仅内部记录，错误与漏洞统一在复盘反馈；开启时保持动态追问，同一知识点默认最多连续追问 2–3 层。
